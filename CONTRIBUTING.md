# Contributing to VulnStack

Thanks for helping. This page covers setup, conventions and the release process. By participating you agree to the [Code of Conduct](CODE_OF_CONDUCT.md). For security issues, see [SECURITY.md](SECURITY.md) instead of opening a public issue.

## Prerequisites

- Node.js 22.12 or newer
- pnpm 12 (the repo pins `packageManager: pnpm@12.11.2`; use Corepack: `corepack enable`)
- Docker, only if you work on the compose setup

pnpm is configured conservatively (`pnpm-workspace.yaml`): dependency build scripts are blocked unless listed in `allowBuilds` (currently only `esbuild`), and pnpm's `minimumReleaseAge` policy delays very fresh package versions (not overridden in this repo). If an install fails because of either policy, do not disable it; ask in the PR or issue, and add an `allowBuilds` entry only for a dependency that truly needs a build step.

## Setup

```sh
git clone https://github.com/vulnstack/vulnstack.git
cd vulnstack
pnpm install
pnpm build
pnpm test
node apps/cli/dist/index.js scan fixtures/npm/lock-v3-express
```

Run the web app locally with `pnpm --filter @vulnstack/web dev`. Without `DATABASE_URL` it uses PGlite in `apps/web/.data/`.

## Scripts

| Command              | What it does                              |
| -------------------- | ----------------------------------------- |
| `pnpm build`         | `turbo run build` for all packages        |
| `pnpm test`          | `turbo run test` (Vitest)                 |
| `pnpm test:coverage` | Tests with coverage                       |
| `pnpm typecheck`     | `turbo run typecheck` (strict TypeScript) |
| `pnpm lint`          | ESLint (`eslint .`)                       |
| `pnpm format`        | Prettier, write                           |
| `pnpm format:check`  | Prettier, check only (CI runs this)       |

Turbo caches task output; use `--filter=<package>` (for example `pnpm turbo run test --filter=@vulnstack/core`) to work on one package. CI runs build, typecheck, test, lint and format check.

## Repository layout

| Path            | Contents                                                           |
| --------------- | ------------------------------------------------------------------ |
| `packages/core` | Scanning engine, ecosystem plugins, reporters (framework-agnostic) |
| `packages/db`   | Drizzle schema, migrations, Postgres / PGlite client               |
| `apps/cli`      | The `vulnstack` command                                            |
| `apps/web`      | Next.js web app and REST API                                       |
| `fixtures/`     | Lock files and manifests used by tests                             |
| `docs/`         | Documentation and the JSON report schema                           |

## Testing conventions

- **No network in tests.** Inject `fetch` into the code under test. Use the helpers in `packages/core/test/helpers.ts` (`fakeOsv`, `ghsa`, `json`, `FIXTURES`). A test that reaches the internet is a bug.
- **PGlite for database tests.** Use in-memory PGlite with the real migrations, never a mocked database.
- **Fixtures** live in `fixtures/<ecosystem>/<case>/` and document themselves in `fixtures/<ecosystem>/README.md`. They deliberately pin **known-vulnerable versions**. Never run an install, build or lock-file update inside `fixtures/`, and do not point tools such as Dependabot at them.
- Prefer files generated by the real package manager; mark hand-written fixtures as such.
- Bug fixes come with a regression test. Changes to report output update the schema in `docs/report-schema.json` and `docs/report-format.md`.

## Coding conventions

- ESM everywhere. Relative imports in TypeScript include the `.js` suffix (`import { x } from './x.js'`).
- Use `import type` for type-only imports.
- Strict TypeScript (`strict`, no `any` without a reason). Prefer small pure functions; keep I/O behind injectable interfaces (`FetchFn`, `FileProvider`, `CacheStore`).
- Comments explain **why**, not what.
- Never put secrets (tokens, API keys) in code, fixtures, logs or test output.
- Run `pnpm format` before committing; CI fails on formatting differences.

## Commits and pull requests

- Small, focused PRs. Describe the problem, the approach and how you tested it.
- Commit messages: imperative mood, a short subject (about 72 characters), body for the why. Conventional prefixes (`feat:`, `fix:`, `docs:`, `test:`, `chore:`) are welcome.
- Make sure `pnpm build && pnpm typecheck && pnpm test && pnpm lint && pnpm format:check` pass.
- User-visible changes update the README or the relevant page in `docs/`.
- Dependencies: add the minimum, justify new ones in the PR, and keep `pnpm-lock.yaml` in sync.

## Releases

Maintainers release by tagging:

1. Bump the version in `apps/cli/package.json` and merge to `main`.
2. Tag `vX.Y.Z` (matching that version) and push the tag.
3. The `Release` workflow verifies the tag against the CLI version, builds and tests, publishes the CLI to npm **with provenance**, then builds and pushes the web Docker image to GitHub Container Registry.
